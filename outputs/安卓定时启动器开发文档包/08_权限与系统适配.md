# 权限与 Android 系统适配

## 1. 必需与可选权限

```xml
<uses-permission android:name="android.permission.SCHEDULE_EXACT_ALARM" />
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
<uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED" />
```

| 权限/能力 | 何时需要 | 产品处理 |
|---|---|---|
| `SCHEDULE_EXACT_ALARM` | `setExact*` 与 `setAlarmClock`，Android 12+ | 保存任务前/后调用 `canScheduleExactAlarms()`；未授权时跳转 `ACTION_REQUEST_SCHEDULE_EXACT_ALARM`。 |
| `POST_NOTIFICATIONS` | Android 13+ 显示保底通知 | 在用户创建首个任务后解释用途再请求。拒绝时仍可调度，但无通知保底。 |
| `RECEIVE_BOOT_COMPLETED` | 开机、应用升级后恢复 | 静态 Receiver 重算启用任务。 |
| 包可见性 `<queries>` | 发现/启动其他应用 | 声明 `ACTION_MAIN` + `CATEGORY_LAUNCHER` 的查询；不申请 `QUERY_ALL_PACKAGES`。 |
| 忽略电池优化 | 非默认必要 | 设置页提供说明；仅由用户主动选择跳转系统页面。 |

不要把 `USE_EXACT_ALARM` 当成普通工具类 App 的通用解决办法。该权限用于闹钟/日历等合资格类别，且分发平台可能审核其使用。个人自用默认采用用户可见的 `SCHEDULE_EXACT_ALARM` 授权路径。

## 2. 精确闹钟策略

| 条件 | 调度方式 |
|---|---|
| 已获精确授权、需要准点 | `setExactAndAllowWhileIdle(RTC_WAKEUP, ...)`。 |
| 已获精确授权、明确以闹钟形态展示 | 可选 `setAlarmClock()`；不要只为绕过后台限制滥用。 |
| 未获授权 | 不注册精确闹钟；标记待授权。可选提供不精确通知模式。 |
| 用户撤回授权 | 系统会删除已登记的精确闹钟；监听状态变化并在首页刷新。 |

`setExactAndAllowWhileIdle()` 在 Doze 下可触发，但同一应用的此类闹钟频率仍受系统配额约束；本产品的“每个任务每天一次”正常情况下不会碰到九分钟频率限制。

## 3. 后台启动限制：必须诚实处理

Android 10（API 29）开始限制后台 Activity 启动，Android 14+ 进一步加强 PendingIntent 相关规则。`AlarmReceiver` 内调用 `startActivity()` 可能在某些状态、系统版本或厂商 ROM 下无法让目标应用前台可见。

### 执行策略

1. 用户在前台创建任务，清楚看到“尝试启动”语义。
2. 触发时尝试 `startActivity(launchIntent.addFlags(FLAG_ACTIVITY_NEW_TASK))`。
3. 立刻写 `LAUNCH_REQUESTED`，不虚报 `SUCCESS`。
4. 按用户选择或异常路径发布通知，用户点按“打开”后启动目标应用。
5. 日志页显示“系统可能拦截后台启动”的提示和时间线。

不要把 `setAlarmClock()` 视为“后台 Activity 启动的万能通行证”。它保证闹钟交付、且系统可显示闹钟信息，但不等于授予任意第三方 App 前台拉起的永久能力。

## 4. Receiver 声明与恢复事件

```xml
<receiver
    android:name=".platform.receiver.AlarmReceiver"
    android:exported="false" />

<receiver
    android:name=".platform.receiver.RescheduleReceiver"
    android:exported="false">
    <intent-filter>
        <action android:name="android.intent.action.BOOT_COMPLETED" />
        <action android:name="android.intent.action.MY_PACKAGE_REPLACED" />
        <action android:name="android.intent.action.TIME_SET" />
        <action android:name="android.intent.action.TIMEZONE_CHANGED" />
    </intent-filter>
</receiver>
```

Android 13+ 若用户将应用设为“受限”，`BOOT_COMPLETED` 可能直到用户再次打开应用才投递。应用每次进入前台都要调用 `rescheduleAll(ON_APP_FOREGROUND)`，并在首页明确显示该限制。

## 5. 国产 ROM 与电源管理

| 现象 | 产品处理 |
|---|---|
| 后台受限/省电策略 | 设置页说明如何在当前 ROM 的电池管理中允许后台运行；不假设专属设置 Intent 一定存在。 |
| 自启动开关 | 仅提供文字指引，不依赖不可移植的厂商私有 Intent。 |
| 前台服务 | 默认不用；精确闹钟与 Receiver 不应依赖常驻服务。 |
| 用户强制停止应用 | Android 会取消相关计划且广播不再正常运行；只能提示用户重新打开应用并重算。 |

## 6. 版本测试矩阵

- 最低：Android 8（API 26），验证基本闹钟、重启、应用选择。
- 主力：Android 12、13、14、16，验证精确权限、通知权限、后台限制变化。
- 自用目标机：至少覆盖实际使用的 ROM（例如 OriginOS/MIUI/ColorOS 的其中一种）和省电模式。
